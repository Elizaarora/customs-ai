# Decisions and assumptions

## ASSUMPTION — 8 synthetic PDF fixtures, scenario mapping
Asked for 8 PDFs covering 6 named scenarios (clean shipment, SHP-24811, SHP-24812,
bad invoice total, packages mismatch, low-quality scan). A shipment needs up to 3
documents (invoice, packing list, bill of lading), so 6 scenarios don't map 1:1 to
8 files. Chose: full 3-document sets for the clean shipment and SHP-24811 (3+3),
the single invoice for SHP-24812 (1, per brief), and one standalone bad-invoice-total
invoice (1) = 8. "Packages mismatch" and "skewed low-quality scan" were left out to
fit the count — ask if those should replace one of the above or be added as a 9th/10th.
Generated by `scripts/generate-fixture-pdfs.mjs`, output to `fixtures/pdfs/` (gitignored,
regenerate with `npm run fixtures:pdfs`).

## ASSUMPTION — No passwords, pick-a-user login
"Add auth with two seeded users" was implemented as a dev-style login screen: it lists
the 2 seeded users (one EXECUTIVE, one MANAGER) and clicking one signs you in as them,
no password. This is a desktop-only internal broker tool with fake data and no real
email, so a password/reset/SSO flow isn't in the brief. The session is a signed,
httpOnly JWT cookie (`SESSION_SECRET` env var), not a password credential. If real
auth is ever wanted, swap the login screen's click-to-sign-in for a credentials form —
`src/lib/session.ts` and `src/lib/auth.ts` (`requireRole`) don't need to change.

## NOTE — This project is on Prisma 8's new "contract" ORM, not classic Prisma Client
`package.json` already had `prisma@^8.0.0-rc.30` before this session touched it. Prisma 8
replaced the classic `schema.prisma` + `new PrismaClient()` + `prisma.user.findMany()` API
entirely:
- The schema lives at `src/prisma/contract.prisma` (not `prisma/schema.prisma`), and
  `prisma contract emit` (re)generates `contract.json` + `contract.d.ts` from it — run
  this after every schema edit, or the app imports stale types.
- Queries go through `db.orm.public.<Model>` from `src/prisma/db.ts`, e.g.
  `db.orm.public.User.where({ id }).first()`, `db.orm.public.User.create({ ... })`.
  There is no `@prisma/client` package in this project anymore — it was removed.
- First-time DB setup is `prisma db init` (not `prisma migrate dev`), and needs a real
  `DATABASE_URL` in `.env`, which doesn't exist in this sandbox — so none of the
  Prisma-backed code (seed script, login page, `requireRole`) has been run against a
  real database. Everything has been verified as far as this environment allows:
  it typechecks (`npx tsc --noEmit`), lints clean, and `node_modules/@prisma/orm-postgres`
  reports the exact expected `DRIVER.NOT_CONNECTED` error (not a code bug) when the
  login page tries to read the seeded user list.
- Full reference docs for this version are vendored at
  `node_modules/@prisma/orm-postgres/skills/prisma-8/references/*.md` — read `contract.md`
  before changing the schema and `queries-postgres.md` before writing new queries.

## DECISION — Extraction uses Gemini, not Claude, on the user's explicit request
CLAUDE.md just says "a vision AI model." Defaulted to Claude (`claude-opus-5-5`) in the
initial plan; the user asked for a free option instead. Verified Gemini's free tier is
real (confirmed live against the user's own API key — `GEMINI_API_KEY` in `.env`,
gitignored) but tightly rate-limited: ~5 requests/minute. Using `gemini-3.6-flash`
(labeled "Stable" in Google's model list) — `gemini-3.8-flash` ("New") returned
`503 high demand` on every attempt when tested live, `gemini-3.6-flash` worked first try.
If `gemini-3.6-flash` is later deprecated, check `https://aistudio.google.com/docs/models`
for its replacement before swapping the `MODEL_ID` constant in `src/lib/extraction/extract.ts`.
Structured output and content-part shapes (`response_format`, `type: "document"/"image"`)
were confirmed against live docs during implementation, not assumed from training data —
Gemini's API, like everything else so far in this project, has moved since any model's
training cutoff.

## ASSUMPTION — Upload validation defaults
`MAX_UPLOAD_BYTES` (10MB) and `ALLOWED_MIME_TYPES` (PDF, PNG, JPEG) in
`src/lib/documents/upload-validation.ts` are proposed defaults, not specified in the
brief. Adjust the constants directly if you want different limits.

## ASSUMPTION — Extraction confidence threshold
`CONFIDENCE_THRESHOLD = 0.8` in `src/lib/extraction/extract.ts` decides AUTO vs.
NEEDS_REVIEW for every extracted field and line item. Not specified in the brief —
same spirit as the cross-check tolerances: you decide the real number.

## DECISION — Cross-checks run after each extraction, not at read time
`runChecksForShipment` (src/lib/run-checks-for-shipment.ts) is called once per document,
right after that document's extraction succeeds (wired into extract.ts). It is NOT called
every time the gate/page reads check results — if it were, re-running checks on every page
load would immediately overwrite a manual "resolved" mark with a fresh unresolved row,
making resolution impossible. `CheckResult` is append-only (no unique constraint, matching
`FieldEdit`/`Approval`); `export-gate.ts` reads the latest row per check name. There is no
"mark check resolved" action yet — that belongs to the review screen (still unbuilt), so a
genuine FAIL currently has no way to become resolved short of a DB edit. Worth building
`resolveCheck` before this is used for real.

## ASSUMPTION — Export CSV shape
One row per invoice line item, shipment-level fields repeated per row:
`reference, containerNumber, packagesCount, grossWeightKg, description, quantity, unitPrice, lineTotal`.
Not specified in the brief (see `src/lib/export/csv.ts`). `containerNumber`/`packagesCount`
are read from the invoice's extracted fields, `grossWeightKg` from the packing list's.

## ASSUMPTION — Approval requires the other 3 gate conditions already met
A manager can't approve a shipment that's still missing documents, has fields needing
review, or has an unresolved failed check — `approveShipment` re-runs the gate (with
`hasApproval` forced to `true`) and throws if anything else is still blocking. Not stated
explicitly in the brief, but matches "the manager approves" meaning the review is done.

## DECISION — Review screen built; LineItem edits are confirm-only
`app/shipments/[id]/review/page.tsx` is the document-left/fields-right review screen.
Fields (`ExtractedField`) can be edited and confirmed, both writing a `FieldEdit` row
(hard rule #4). `LineItem` rows can only be confirmed, not edited — `FieldEdit`'s foreign
key points at `ExtractedField` only, so there's no audit trail for a line item edit in the
current schema. If line-item editing is needed, add a nullable `lineItemId` to `FieldEdit`
(or a parallel `LineItemEdit` table) first.

Editing a field re-runs all cross-checks for the shipment immediately (same
`runChecksForShipment` used after extraction), so a corrected value can flip a FAILED
check to PASS without waiting for a re-upload.

## FIX — Gemini client needed v1beta explicitly
`new GoogleGenAI({})` defaulted to the stable v1 API, which rejects `type: "document"`
content parts (PDF input) — confirmed live against the real API with a 400 naming the
exact issue. Fixed with `httpOptions: { apiVersion: 'v1beta' }` in `extract.ts`.

## FIX — LineItem duplication on re-extraction
`LineItem` has no unique constraint to upsert on (unlike `ExtractedField`), so
re-extracting a document (e.g. after a re-upload) was appending new line items
alongside the old ones instead of replacing them. Fixed by deleting a document's
existing `LineItem` rows before writing the new ones, inside the same transaction.

## DECISION — Design system built, light mode only, Geist kept
`src/components/ui/` has all 14 requested components (Button, Input, Select, Badge,
Card, Table, Tabs, Dialog, Toast, Skeleton, EmptyState, ErrorState, Spinner, Tooltip),
tokens in `app/globals.css` (neutral slate scale, one indigo accent, amber/red/green
semantic pairs), `src/components/app-shell.tsx`, and `/dev/ui` showing every component.

Two deliberate choices, not specified in the brief:
- **Light mode only** — dropped the old boilerplate's `prefers-color-scheme: dark`
  block. This is a calm, all-day desktop tool with no dark-mode ask; keeping one mode
  halves the number of color combinations to contrast-check.
- **Kept Geist instead of switching to Inter** — already wired via `next/font` in
  `app/layout.tsx`, equally minimal/professional. Easy to swap if you want Inter.

**`ErrorState.retry` and `AppShell.signOutAction` take a pre-built `ReactNode`, not a
callback function.** Every screen in this app is a Server Component (auth checks,
DB reads). A Server Component can't pass a plain JS function as a prop to a Client
Component — only Server Actions cross that boundary. So both props expect an
already-wired action element (e.g. `<form action={...}><Button>Retry</Button></form>`),
same pattern as `EmptyState.action`.

**Not done yet, on purpose**: the design system exists and is demoed on `/dev/ui`,
but no existing screen (login, shipment list, detail, review) has been restyled to
use it — that's explicitly a separate task so its own before/after diff stays clean
and doesn't get tangled with this one.

## DECISION — Restyled every real screen with the design system; no `loading.tsx` on auth-gated routes
Login, shipment list, shipment detail, and the review screen now use `AppShell` +
`src/components/ui` exclusively — no raw Tailwind colors/spacing/font-sizes left in
any of them. Added `error.tsx` boundaries for `/`, `/shipments/[id]`, and
`/shipments/[id]/review` using `ErrorState`.

**Did NOT add `loading.tsx` to those same three routes, despite the original ask** —
tried it, and it broke a real security property. Every one of these routes starts
with `requireRole`, which `redirect()`s unauthenticated requests to `/login`. Adding
a `loading.tsx` makes Cache Components treat the route as Partial-Prerender-eligible:
the page gets wrapped in a Suspense boundary, so the server sends a `200` static
shell immediately and the auth redirect happens inside a *streamed* RSC chunk
instead. A browser's React runtime follows that embedded redirect instruction
fine, but anything else — `curl`, a health check, a bot, a server-to-server call —
sees a bare `200` with no real content, not the `307` it should get. Verified this
directly: with `loading.tsx` present, `curl /` returned `200`; removed it, same
route returned the correct `307`. Since every one of these pages is *entirely*
behind an auth gate (there's no public shell worth showing a skeleton for anyway),
the fix is to just not use the `loading.tsx` convention on them. `/dev/ui` doesn't
have this file either, for the same reason.

## DECISION — Built the gap list: schema migration, richer extraction, manual entry, override, accuracy report
In response to "build all the missing features" after comparing against the real client
brief (not just `CLAUDE.md`'s condensed version). What changed:

- **Schema migration** (applied live, see `migrations/app/20261107T1033_expand_schema`):
  `CheckResult.passed` (Boolean) → `status` (`PASSED|FAILED|CANNOT_CHECK`, nullable —
  made nullable rather than backfilled, since the 18 pre-migration test rows in the dev
  DB are worthless fake data and a backfill migration wasn't worth authoring for them);
  added `CheckResult.involvedFieldIds` (`Int[]`) and `resolutionNote`; added
  `FieldEdit.type` (`EDIT|CONFIRM|OVERRIDE|MANUAL_ENTRY`, also nullable for the same
  reason), and `FieldEdit.lineItemId` (nullable, alongside now-nullable `fieldId`) so a
  `LineItem` confirmation finally has an audit trail; added `LineItem.hsn`; added a new
  `ExportLog` table.
- **Extraction fields expanded** to match the brief: shipper, consignee, invoice/BL
  number, date, currency, Incoterm (common to all 3 doc types) and HSN per line item.
  No schema change was needed for the header fields — `ExtractedField.name` was always
  a free string — just `src/lib/extraction/field-config.ts`'s expected-field lists and
  the prompt.
- **`CANNOT_CHECK` is now persisted**, not skipped — `run-checks-for-shipment.ts` writes
  a real row for every check, every time.
- **A FAILED check now flags its involved fields `NEEDS_REVIEW`** automatically, per the
  brief's own rule.
- **Override mechanism**: the old bare "mark resolved" button is gone. A FAILED check
  can now only be cleared by correcting a value (re-runs the check) or by an override
  with a mandatory note (`overrideCheck` action), which writes `CheckResult.resolutionNote`
  plus a `FieldEdit` of type `OVERRIDE` for every involved field.
- **Manual entry** for a document whose extraction failed completely: a form on the
  review screen (shown automatically when a document is `FAILED` with zero fields),
  listing exactly the fields that would have been extracted; each saved value becomes
  an `ExtractedField` with `status: MANUAL` and a `FieldEdit` of type `MANUAL_ENTRY`.
- **Accuracy report** (`/reports/accuracy`): per-field and per-supplier tables. "Accuracy"
  is a proxy — a field is counted accurate if it was never through an `EDIT`, not a
  measurement against verified ground truth (there is none in this project). Supplier
  is read from the invoice's `shipper` field, not a separate schema entity.
- **Export CSV expanded** to the new fields (shipper, consignee, document number, date,
  currency, Incoterm, HSN) and now writes an `ExportLog` row (who, when, row count) —
  the export audit trail that didn't exist before.
- **Fixed a factual data error**: the fixture generator had `SHP-24812`'s gross weight
  as 980kg — the real brief's sample data says 1460kg. Regenerated
  `fixtures/pdfs/shp24812-invoice.pdf` with the correct value, and added
  shipper/consignee/date/Incoterm (with the brief's actual supplier names, Company
  B/China and Company C/Sweden) to every fixture document so the new extraction fields
  have something real to extract.

**Deliberately not built in this pass** — not codeable, or not actually asked for by
the real cross-check requirements:
- **Currency/consignee cross-checks** — the real brief's cross-check list is "invoice
  total vs line sum, packages and weights across all three documents" only; currency/
  consignee consistency was from an earlier, more elaborate plan that was never part
  of the actual brief. Skipped to avoid building something unrequested.
- **Gross weight across the bill of lading too** — the brief's own sample data table
  has no weight column for the bill of lading; the existing invoice-vs-packing-list
  check already matches the given SHP-24811 scenario exactly. Left as a 2-document
  check rather than inventing a third data point the brief doesn't model.
- **India hosting, a no-train AI provider, DPDP compliance** — see `docs/TDD.md` §10.
  None of these are code changes; they need a real paid account/contract decision, a
  cloud region choice, and legal/consent work respectively. Stated plainly there as
  unmet, not quietly implied as done.
- **Skewed or bilingual scan testing** — never built; would need actual scanned-image
  fixtures (our generator only produces clean text PDFs via pdf-lib) and, for
  Devanagari or other non-Latin scripts, a different font entirely (Helvetica has no
  glyphs for it). Flagged, not attempted, given the time this would take relative to
  the other gaps.
- **Approval `decision`/`comment` (a manager "send back" flow)** — was in an earlier
  schema plan, not re-raised as a priority gap against the real brief; skipped this
  round.

## DECISION — Manager "send back", and a real skewed-scan fixture
Closed two of the previously-deferred items:

- **`Approval.decision`/`comment`** (migration applied live, additive, no data loss):
  a manager can now `sendBackShipment` with a mandatory comment at any point — unlike
  approving, this isn't gated on the review being complete, since it's a flag for the
  team, not a completion signal. `hasApproval` in the export gate now only counts a
  `SENT_BACK` row as *not* an approval; a null `decision` (the one pre-migration test
  row) still counts as approved, since `SENT_BACK` didn't exist when it was written.
- **`fixtures/pdfs/skewed-invoice.pdf`**: pdf-lib's page-level `setRotation` only
  accepts multiples of 90°, which doesn't simulate a crooked scan — real skew needed
  `rotate: degrees(n)` on every individual `drawText` call. Built a 4°-tilted invoice
  and verified live against the real Gemini API that it still extracts the total and
  shipper name correctly. **Bilingual documents are still not attempted** — the
  standard Helvetica font pdf-lib embeds has no Devanagari (or other non-Latin) glyphs,
  so a real bilingual fixture needs embedding a different font entirely, which wasn't
  worth the time relative to everything else on the list. Fixture count is now 9, not
  the originally-scoped 8 — noting the drift from that earlier assumption rather than
  silently changing it.

## FIX — Disabled Cache Components after a production-only redirect bug
Deploying to real Vercel infrastructure surfaced a bug `next dev` never showed:
with the experimental `cacheComponents` flag on, a `redirect()` thrown mid-render
on a route with no static content for a logged-out visitor (the root `/`) leaked
as a raw RSC digest string in a cached 200 response instead of becoming a real
HTTP 307 — meaning every signed-out visitor hit a broken page in production,
not a redirect to `/login`. Confirmed by building and running `next start`
locally: same broken response. Turned `cacheComponents`/`partialPrefetching`
off in `next.config.ts` and removed the now-invalid `export const instant =
false` route config from the 6 pages that had it; `next build` + `next start`
locally now returns a real `307` with `Cache-Control: private, no-cache,
no-store`. This is the second Cache-Components-related redirect bug this
project has hit (the first was the `loading.tsx` one) — an experimental
rendering feature breaking the single most basic flow (visiting the site
signed out) twice is reason enough to just turn it off rather than keep
chasing narrower workarounds.

## FIX — Real Vercel deploy: pooler DB connection, and a graceful 404 for missing files
Deploying for real to Vercel surfaced two more issues `next dev` and local
testing never would have:

- **`getaddrinfo ENOTFOUND db.<ref>.supabase.co`**: Supabase's direct database
  hostname only resolves over IPv6 by default, and Vercel's serverless
  functions have no outbound IPv6 — every query failed. Fixed by switching
  `DATABASE_URL` (production only; local dev still uses the direct connection,
  which works fine from this machine) to Supabase's transaction-mode
  connection pooler (`*.pooler.supabase.com:6543`, username
  `postgres.<project-ref>`), which is IPv4-reachable.
- **Documents uploaded in dev (disk storage) 500'd when viewed on the live
  Vercel deployment (Supabase storage)**: expected, since the two environments
  use different storage backends by design — but the route let the missing-file
  error crash into a 500 instead of a clean 404. Fixed: `readFile` is now
  wrapped in a try/catch in the document-serving route.

## NOTE — Extraction runs synchronously inside the upload request
`uploadDocument` awaits `extractDocument` before redirecting, so the upload request
is slow (seconds) while Gemini responds, and two uploads within the same minute can
hit the 5 req/min free-tier limit (surfaces as a FAILED document with a clear
"rate limited" error, not a crash — hard rule #3). No background job queue was
built since this is a low-volume internal tool; revisit if that changes.

## REVIEW — Strict audit findings and fixes
A full pass against: auth/role checks, server-side Zod validation, secrets,
authenticated file serving, loading/empty/error states, the edit log, visual
tokens, keyboard/contrast, and lint/typecheck/tests. Fixed: `editField` now
validates with Zod instead of a manual trim check; raw `Number(id)` route-param
parsing (4 call sites) replaced with a validated `parseShipmentId` helper,
invalid ids now 404 instead of flowing a `NaN` into a query; `.env.example` was
missing `GEMINI_API_KEY` and `NEXT_SERVER_ACTIONS_ENCRYPTION_KEY`; the review
screen's and login screen's missing-data cases used plain text instead of
`EmptyState`. Confirmed clean (no fix needed): requireRole coverage, no secrets
in git history or tracked files, uploads served only through the authenticated
route, no raw Tailwind colors left in any restyled screen, no `div onClick`
keyboard traps.

Confirmed, not fixed (real limitations, carried into the TDD): `LineItem`
confirmations have no audit trail (schema gap); there's no override mechanism
with a mandatory note; `CANNOT_CHECK` results aren't persisted, only skipped;
`CheckResult.passed` is a boolean, not the tri-state status a real system
would want; there's no manual-entry path for a document whose extraction fails
completely; there's no export audit log.

## DECISION — Excel export alongside CSV
The brief asks for export "in the filing software's Excel import layout" — the
app only had CSV. Added `?format=xlsx` to the existing export route (CSV stays
the default, so nothing that already depends on it breaks) using the same
15-column shape and the same server-side gate check as CSV; the real filing
software's exact column layout was never specified, so this is the project's
own shape in spreadsheet form, same as the CSV one already was.

Picked `exceljs` over the more common `xlsx` (SheetJS) package: `npm audit`
showed `xlsx` carries two unpatched high-severity CVEs (prototype pollution,
ReDoS) with no fix available on the npm registry, which fails hard rule #6
("be careful not to introduce vulnerabilities") on a brand-new dependency
with zero offsetting benefit. `exceljs` only has a minor transitive advisory.

One test-only wrinkle, not a real bug: this project's dependency tree has
three different `@types/node` versions installed at once (root `^20`, a
newer one pinned under `@prisma`, an older one under `exceljs`'s own
`fast-csv` dependency), so TypeScript sees two structurally different
`Buffer` declarations depending on which package's `.d.ts` is doing the
referencing. The round-trip test that reloads the generated workbook has to
cast through `any` at that one boundary to bridge them; the actual bytes are
unaffected; `tsc --noEmit`, lint, and `vitest run` (34/34) are all clean.

## DECISION — Responsive (phone) layout, overriding the earlier "desktop only" rule
`CLAUDE.md`'s hard rules say "Desktop only" and list "mobile layout" under
out-of-scope — but the external assessment rubric explicitly requires "a
layout that works on a phone." Flagged this direct conflict to the user; they
chose to satisfy the rubric, so this one requirement now overrides that
earlier scope line.

Added responsive breakpoints (Tailwind `sm:`/`lg:`) to every screen rather
than building separate mobile views: the sidebar in `AppShell` collapses and
its label moves into the header below `sm`; the review screen's side-by-side
document/fields grid (the one place "document on the left, fields on the
right" was a hard layout requirement) stacks to a single column below `lg`
and switches back to two columns above it, since that split only makes sense
once there's enough width for both panes to be readable; every form row that
pairs an `Input` with a `Button` wraps instead of overflowing on narrow
viewports; both report tables sit in a horizontally-scrollable wrapper as a
safety net. Verified via `tsc`/`lint`/`vitest` (unchanged, all pass) and a
live curl check that the new breakpoint classes render; no browser/visual
screenshot tool was available in this environment to confirm the rendered
result at an actual phone viewport, so that's a known verification gap worth
a manual check before treating this as fully proven.
